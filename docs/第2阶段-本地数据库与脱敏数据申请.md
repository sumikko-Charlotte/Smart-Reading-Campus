## 一、这一块解决了什么

| 组会要求 | 落地情况 |
|---|---|
| 本地数据库搭建 | SQLite 单文件库（`backend/smart_reading.db`），13 张表；用 Alembic 做版本化迁移，不再靠手写 SQL 打补丁 |

## 二、为什么本地先用 SQLite

| 维度 | SQLite（本轮） | MySQL 8（上云后） |
|---|---|---|
| 部署 | 零安装，一个文件，组员拷走就能跑 | 需要服务端，但学校/云主机都现成 |
| 并发 | 写串行，够 5~10 人演示 | 支持高并发与连接池 |
| JSON 字段 | 存文本，应用层解析 | 原生 JSON，可建函数索引 |
| 迁移 | 文件复制即备份 | mysqldump / 云厂商快照 |
| 适用阶段 | 开发、组会演示、离线跑数据 | 小程序上线、多人同时使用 |

结论：**开发期用 SQLite，把「表结构」和「数据访问」做成与数据库无关**；等小程序端要上线、或者要跑真实的几万条借阅数据时再切 MySQL，代码不用改。

> 已经在 `backend/app/core/config.py` 里预留了 MySQL 连接串示例，切换时只改 `.env` 的 `DATABASE_URL`。

## 三、表结构总览

13 张业务表，分四层：

```text
账号与权限
  users ──────────────┬── permission_logs（谁改了谁的权限）
                      └── （角色默认权限 + 额外授予/收回，存在 users 的 JSON 字段里）

阅读推广活动
  activities ──┬── activity_signups（报名 / 签到）
               ├── activity_summaries（活动总结）── notifications（推送）
               └── certificates（电子证书，含验真码）

图书与流通
  books ──┬── drift_records（漂流单册：当前持有者、流转次数）
          ├── borrow_records（借阅记录）★ 本轮新增
          └── book_favorites（收藏与评分）★ 本轮新增

智能体数据
  reading_events（检索 / 浏览 / AI 互动 / 报名 / 读推送）★ 本轮新增
  ai_conversations（伴读、推荐、文案生成的会话记录）
```

★ 为本轮为第三块「智能体」新增的表。完整字段见 `docs/数据字典.md`，关键设计取舍：

| 设计点 | 做法 | 原因 |
|---|---|---|
| 借阅记录与读者的关联 | `borrow_records.reader_hash`（脱敏 ID）+ 可空 `user_id` | 学校给的是哈希后的读者号；能匹配上的回填 `user_id`，匹配不上的也保留，可用于统计「多少借阅来自未注册学生」 |
| 行为埋点只记「谁对什么做了什么」 | `reading_events` 存事件类型、对象 ID、检索词、停留时长 | 不存正文与聊天内容，降低隐私风险；画像所需的信号已足够 |
| 收藏单独建表 | `book_favorites(user_id, book_id)` 唯一 | 显式偏好信噪比最高，比点击更可靠；同时支撑前端「我的书架」 |
| 书目补齐馆藏字段 | 中图法分类号、索书号、页数、定价、目录、馆藏地 | 「AI 录书」要自动填的就是这些；「AI 伴读」的导读依赖目录 |
| 不建全文表 | 暂不存图书全文 | 版权风险高，且课程项目用摘要 + 目录已能做出导读效果 |

## 四、迁移机制（Alembic）

### 4.1 为什么换掉手工迁移

第 1、2 轮用的是「启动时检查缺哪列就 ALTER」的补丁式迁移（`_ensure_columns`），好处是省事，坏处是：

- 补丁越堆越多，没人说得清当前库到底处于哪个版本；
- 无法回滚，改错了只能手改数据；
- 上云时这些 SQLite 专用写法（重建表换列）在 MySQL 上不能用。

现在改为 Alembic：**每次表结构变更 = 一个可追溯、可回滚的版本文件**。

### 4.2 目录与版本链

```text
backend/
├── alembic.ini                      # 只放脚本路径，连接串从 settings 读（避免连错库）
├── alembic/
│   ├── env.py                       # 复用应用配置与 ORM 元数据，SQLite 自动开 batch 模式
│   └── versions/
│       ├── 20261019_f63218b637af_baseline_schema.py   # 基线：前两轮的 10 张表
│       ├── 20261019_dfed47ed060b_ai_data_layer.py     # 本轮：3 张新表 + 书目 8 列
│       └── 20261019_a8f8a9ea514b_borrow_reader_hash.py# 本轮：借阅记录加 reader_hash
```

### 4.3 日常命令

```bash
cd backend

# 看当前版本、还差几个迁移
.venv/Scripts/python.exe scripts/migrate.py --status

# 升级（自动先备份，再升级，最后校验模型与库是否一致）
.venv/Scripts/python.exe scripts/migrate.py

# 改了模型之后，生成一条新迁移
.venv/Scripts/alembic.exe revision --autogenerate -m "一句话说明改了什么"
# 生成后务必打开文件核对：autogenerate 会漏掉索引重命名、默认值变更等细节

# 回退一个版本
.venv/Scripts/alembic.exe downgrade -1
```

### 4.4 几个必须知道的坑

1. **SQLite 的 DDL 不在事务里**：迁移中途失败会留下半成品表（本轮就遇到过「表建好了、加列失败」）。所以 `migrate.py` 强制先备份，出问题用 `backup_db.py --restore` 回滚。
2. **SQLite 不能加「NOT NULL 且无默认值」的列**：新列必须带 `server_default`，本轮 `books` 的 8 个新列都按这个规则写。
3. **batch 模式**：改列类型、删列在 SQLite 上要靠「建新表→拷数据→改名」，`env.py` 里对 SQLite 自动开启 `render_as_batch`，迁移文件里会看到 `batch_alter_table`。
4. **老库承接**：已有数据的库不能直接 `upgrade`，要先 `alembic stamp <基线版本>` 告诉它「你已经在基线上了」，再 upgrade（本轮已对现有库执行过）。

### 4.5 应用启动时会自动迁移

`init_db()` 现在的行为：

- 库是空的 → 按模型建表，然后 `stamp head`（新环境一条命令跑起来）
- 库已存在 → `upgrade head`（组员拉代码后启动即自动升级）

## 五、备份与恢复

```bash
cd backend

# 备份（默认保留最近 20 份，存到 backend/backups/）
.venv/Scripts/python.exe scripts/backup_db.py --tag 组会前

# 看有哪些备份
.venv/Scripts/python.exe scripts/backup_db.py --list

# 恢复（会先把当前库再备份一份，防止误操作不可逆）
.venv/Scripts/python.exe scripts/backup_db.py --restore smart_reading_20261019_172331_before_migrate.db
```

用 SQLite 的 `VACUUM INTO` 做快照，比直接复制文件安全（复制到一半可能有写入）。建议节奏：**每次改表结构前、每次组会演示前、每次批量导入数据前**各备份一次。

## 六、数据怎么进来

### 6.1 三类 CSV

| 文件 | 表头 | 说明 |
|---|---|---|
| 学生名单 | `student_no, name(可选), college, major, class_no, grade` | 已存在的学生只更新学院/专业/班级/年级，不会覆盖姓名 |
| 馆藏书目 | `isbn, title, author, publisher, publish_date, clc_code, call_no, pages, price, lib_location, total_copies, available_copies, summary(可选), toc(可选)` | 按 ISBN 幂等：有则补字段，无则新建 |
| 借阅记录 | `reader_no, isbn, borrowed_at, due_at(可选), returned_at(可选), renew_count(可选), barcode(可选), status(可选)` | 按「读者哈希 + ISBN + 借出日期」幂等 |

示例文件在 `backend/samples/`，可直接改造成给老师的模板。

### 6.2 命令

```bash
cd backend

# 先预演，只统计不写库
.venv/Scripts/python.exe scripts/import_school_data.py --students samples/示例-学生名单.csv --books samples/示例-馆藏书目.csv --dry-run

# 正式导入
.venv/Scripts/python.exe scripts/import_school_data.py \
    --students samples/示例-学生名单.csv \
    --books    samples/示例-馆藏书目.csv \
    --borrows  samples/示例-借阅记录.csv

# 如果学校已经给了哈希后的读者号
.venv/Scripts/python.exe scripts/import_school_data.py --borrows 借阅.csv --reader-mode hashed
```

导入结束会打印一行统计，重点关注 `unmatched_reader`（读者号匹配不上）和 `unknown_isbn`（书目里没有这本书）—— 这两个数不为 0 说明两份数据对不上，需要先补书目再导借阅。

### 6.3 脱敏盐值

`reader_no` 为真实学号时，脚本用 **HMAC-SHA256 + 盐** 转成 `u_` 开头的 16 位哈希，再入库。盐值存在 `backend/.data_salt`（已在 `.gitignore` 中，不进仓库）。

> ⚠️ 盐值一旦丢失，历史借阅记录就无法再与新导入的数据关联。请和代码分开保管（比如写进组内共享文档的密码栏），并在换机器时一起带走。

## 七、向老师申请脱敏数据

### 7.1 申请什么

给老师的正式材料是 `docs/数据字段清单-脱敏数据申请.xlsx`，共 5 页：

1. **申请说明** —— 申请方、用途、范围、脱敏要求、数据形式、保管与销毁承诺、合规依据
2. **字段清单** —— 30 个需要学校提供的字段（其余 176 个字段是系统自建，不需要申请）
3. **脱敏规则** —— R1 学号哈希 / R2 姓名不导出 / R3 日期截断到日 / R4 条码可截断
4. **不申请的字段** —— 手机号、身份证、成绩、罚款、住址等，逐条写明原因
5. **数据量估算** —— 让老师评估导出成本（学生 2 万、书目 10 万、借阅 50 万）

### 7.2 申请话术要点

- **说清边界**：只要「借了什么书、什么时候借还」，不要「谁是谁」。姓名、手机号一概不要。
- **主动给方案**：不要问「能不能给学号」，而是「我们用加盐哈希后的读者号，盐由我们保管，您这边导出时按规则处理即可」。
- **降低对方成本**：一次性 CSV 快照即可，不需要开接口、不需要持续对接。
- **给退路**：先要 1 个学期、1 个学院的数据跑通流程，验证有效再申请全量。
- **讲清用途**：只用于校内阅读推广推荐，成果只展示聚合结论（如「计算机学院借阅偏好 TOP10 分类」）。

### 7.3 合规依据

《中华人民共和国个人信息保护法》的「最小必要」与「目的限定」原则：只收集实现目的所必需的信息，且不用于申请之外的目的。这两条正好支撑「不要姓名手机号、只做聚合展示」的方案。

## 八、上云迁移路径

### 8.1 切换步骤

1. **准备库**：在云上建 MySQL 8 实例，`utf8mb4` / `utf8mb4_0900_ai_ci`
2. **建表**：改 `.env` 的 `DATABASE_URL` 为 `mysql+pymysql://user:pwd@host:3306/smart_reading?charset=utf8mb4`，装 `pymysql`，然后 `python scripts/migrate.py` —— 迁移链会在空库上把 13 张表建好（不要导入 SQLite 的 dump，那是另一种方言）
3. **搬数据**：用「导出 CSV → `import_school_data.py` 导入」的方式，或写一次性脚本按表搬运（注意外键顺序：users → books → activities → 其余）
4. **验证**：`alembic check` 无差异；跑 `tests/test_api_smoke.py`；抽查 3 条借阅记录能反查到用户
5. **切换**：小程序端与 PC 端同时改指向新库，观察一天后下线本地库

### 8.2 兼容性差异清单

| 项 | SQLite | MySQL 8 | 本项目怎么处理 |
|---|---|---|---|
| JSON 字段 | TEXT，应用层解析 | 原生 JSON | ORM 用 `sqlalchemy.JSON`，两种库都能跑 |
| 布尔 | 0/1 | TINYINT(1) | `Boolean` 类型自动映射 |
| 时区 | 存字符串，无时区概念 | DATETIME 不带时区 | 统一按 UTC 存（`DateTime(timezone=True)` + 代码里 `utcnow()`），展示层转 +08:00 |
| 字符串长度 | 不强制 | 必须显式 | 模型里全部写了 `String(n)`，这是当初就定好的规矩 |
| 索引与唯一 | 支持 | 支持，但大小写取决于排序规则 | `student_no`、`isbn`、`verify_code` 唯一索引在 `utf8mb4_0900_ai_ci` 下大小写不敏感，正好符合预期 |
| DDL 事务 | 不支持 | 支持（隐式提交） | 上云后迁移更安全，batch 模式可关（`env.py` 已按方言判断） |
| 备份 | 文件复制 / `VACUUM INTO` | `mysqldump` / 云快照 | `backup_db.py` 只处理 SQLite，上云后换运维手段 |

### 8.3 如果学校只认 PostgreSQL

PostgreSQL 反而更贴近：`JSONB` 可索引、`TIMESTAMPTZ` 原生带时区、`ALTER TABLE` 全部支持。把 `DATABASE_URL` 换成 `postgresql+psycopg://...` 即可，迁移链与模型都不用改。这条也写进了备选方案，答辩时可以作为「技术选型有比较」的佐证。

## 十、留给第三块（智能体）的接口

本轮只建表、不写推荐逻辑，第三块会直接在这几张表上做：

| 场景 | 用到的数据 | 已有基础 |
|---|---|---|
| AI 录书 | `books` 的 ISBN / 书名 / 作者 / 中图法分类号 / 索书号 / 页数 / 定价 / 目录 | 字段已就位，缺的是「拍照 → 结构化」的模型调用 |
| AI 匹配 | `borrow_records`（共现矩阵）+ `book_favorites`（显式评分）+ `reading_events`（检索词） | 表与索引已就位，样本数据可跑通链路 |
| AI 触达 | `borrow_records.due_at`（到期提醒）+ `reading_events`（活跃度）+ `notifications` | 推送表已支持按角色分发 |
| AI 伴读 | `ai_conversations` + `books.toc` / `books.summary` | 会话表与书目摘要已有，缺导读 prompt 与知识库 |

下一块要做的第一件事，是把这四个场景分别落到「读哪张表、调哪个模型、产出写回哪张表」，然后逐个替换掉现在写死的 Mock。
