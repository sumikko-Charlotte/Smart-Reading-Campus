# 第 2 阶段 ③：从「接 API」到「接智能体」

> 对应 10-18 组会第三项：把整个项目往智能体方向靠。
> 代码位置：`backend/app/agents/`、`backend/app/api/v1/agent.py`、`web-pc/src/views/agent/`

---

## 一、这次到底改了什么

之前是「接 API」：

```text
用户输入 ──> 拼一段提示词 ──> 调模型 ──> 拿到文字 ──> 前端展示
```

模型不知道馆里有什么书、不知道你是谁、不知道这本书还能不能借。它能做的只是把提示词写得更像人话。

现在是「接智能体」：

```text
用户说目标
   │
   ├─> 模型决定：先查这个人的借阅画像        ← 工具：user_profile
   ├─> 模型决定：按 TP 类找候选              ← 工具：search_books
   ├─> 模型决定：这本还有没有货              ← 工具：book_stats
   ├─> 模型决定：排除他借过的                ← 工具：user_history
   └─> 模型输出推荐 + 理由（理由里带上面查到的证据）
```

差别不在「用了更贵的模型」，而在**模型能不能自己去看数据**。判断标准很简单：
如果换一个模型，业务代码一行不改就能跑，说明这一层做对了；如果换模型就要重写提示词，那还是「接 API」。

## 二、四层结构

```text
┌──────────────────────────────────────────────────────────┐
│  场景层  app/agents/scenes.py                             │
│  intake 录书 │ match 匹配 │ outreach 触达 │ companion 伴读 │
│  职责：校验入参 → 判断能否用模型 → 校验模型输出 → 决定降级  │
├──────────────────────────────────────────────────────────┤
│  运行时  app/agents/runtime.py                            │
│  ReAct 循环：想 → 调工具 → 看结果 → 再想，最多 4 步        │
│  职责：步数、token 预算、工具白名单、超时                  │
├──────────────────────────────────────────────────────────┤
│  工具层  app/agents/tools.py                              │
│  10 个只读工具，各自声明允许在哪些场景被调用               │
├──────────────────────────────────────────────────────────┤
│  模型层  app/services/llm_client.py                       │
│  OpenAI 兼容协议：DeepSeek / 通义 / Ollama 本地，同一套代码 │
└──────────────────────────────────────────────────────────┘
```

分成四层而不是一个大函数，是为了让「换个模型」只动最底下一层，「加个场景」只动最上面一层。

## 三、四个场景

### 1. AI 录书 `POST /agents/intake/run`

**解决什么**：老师拿到一本书，要手工敲书名、作者、出版社、分类号、索书号。一本书三分钟，一批书就是一下午。

**流程**：

```text
输入 ISBN / 书名 / 拍到的整段文字
  → get_book / search_books 查重（馆里已有就别重复录入）
  → 整理成结构化字段
  → 输出置信度 + 缺失字段 + 需人工核对的点
```

**输出示例**：

```json
{
  "duplicate": {"is_duplicate": false, "book_id": "", "reason": "未能匹配到已有馆藏"},
  "book": {"title": "推荐系统实践", "author": "项亮", "clc_code": "TP391", ...},
  "confidence": 0.72,
  "missing_fields": ["call_no", "lib_location"],
  "review_notes": ["本记录需编目老师确认后方可入库"]
}
```

**人工门禁**：AI 永远不直接写库。它只产出草稿，编目老师确认后才入库。理由很实际——分类号错了，这本书在架子上就永远找不到。

**防编造**：模型给出的 ISBN 如果和输入对不上，一律改回输入值；重复书目的 `book_id` 必须能在库里查到，查不到就清空。

---

### 2. AI 匹配 `POST /agents/match/run`

**解决什么**：推荐不能只是「借得最多的十本书」。学生借过 6 本文学书，你给他推 Python 教程，他不会信第二次。

**流程**：

```text
读画像（分类偏好、标签、收藏、活跃度）
  → 召回候选（同分类 / 同标签 / 相似书 / 热门）
  → 排除已借过的
  → 核对可借数量
  → 生成理由，理由必须能对上查到的数据
```

**输出示例**：

```json
{
  "strategy": "profile",
  "items": [{
    "book_id": "bok_xxx",
    "title": "数学分析（上册）",
    "reason": "与你常读的方向一致，数学、分析，馆内可借 4 册。",
    "evidence": ["你借过 6 本 O 类", "累计借出 72 次", "当前可借 4 册"]
  }],
  "explanation": "降级模式：3 本均命中你的借阅偏好（同分类或关键词），未使用语义理解。"
}
```

**防编造（这里最关键）**：模型返回的每个 `book_id` 都要回数据库核对。核对不上的直接剔除；如果全部核对不上，整次结果降级为规则推荐。**宁可给出朴素的推荐，也不给一本不存在的书。**

同时，书名、作者、库存一律以数据库为准，不用模型返回的值——模型可能把作者记错一个字。

---

### 3. AI 触达 `POST /agents/outreach/run`

**解决什么**：活动办得好不好，一半在文案。但让每个办活动的人自己写推文，写出来往往是「兹定于……望周知」。

**流程**：

```text
查活动真实信息（时间、地点、名额、是否发证书）
  → 查报名人群的学院与年级分布
  → 写标题 / 正文 / 推送摘要
  → 标出发布前需要人工确认的点
```

**约束写进提示词了**：

- 名额、时间、地点必须与工具返回一致，拿不到的信息不写
- 不用「最」「第一」「唯一」等绝对化表述
- 不做承诺性说法

**人工门禁**：`needs_human_approval: true` 是固定返回。AI 只出草稿，不自动推送。文案发出去代表学校，这一步不能交给模型。

> 范围说明：本次实现聚焦「活动推广文案」。落地清单里提到的「借阅到期提醒」属于同一套工具集的下一个扩展（`user_history` 已经能取借阅与应还日期），等真实借阅数据进来再接更合适——现在模拟数据的到期时间是造的，提醒了也没意义。

---

### 4. AI 伴读 `POST /agents/companion/run`

**解决什么**：学生问「这本书在哪个馆藏区」，普通聊天机器人答不了。

**流程**：

```text
判断问题类型
  ├─ 问具体某本书 → get_book，回答带索书号与馆藏地
  ├─ 问某类书     → search_books，再决定要不要 similar_books 延伸
  ├─ 问个人借阅   → user_history（只读自己）
  ├─ 问活动       → list_activities
  └─ 闲聊/观点    → 不调工具，直接聊
```

**输出带引用**：`citations` 里每条引用都要能在库里查到对应的书或活动，编造的引用直接剔除。问题里有书名时，回答会带上「沙河二层 C 区，索书号 K02/HL11，可借 1 册」这种能直接用的信息。

## 四、10 个工具

工具是智能体的手。设计上有三条硬规矩：

1. **只读**。除录书由前端保存草稿外，智能体不改业务数据。
2. **不返回整条记录**。只挑决策需要的字段，长文本截断，否则一次工具结果就能吃掉整个上下文。
3. **失败不抛异常**。返回 `{"ok": false, "error": "..."}` 让模型自己纠错，一次参数写错不该让整次对话挂掉。

| 工具 | 作用 | 允许的场景 |
|---|---|---|
| `search_books` | 按关键词/分类检索馆藏 | 四场景全部 |
| `get_book` | 按书名或 ISBN 取完整馆藏信息 | 四场景全部 |
| `book_stats` | 近 180 天借阅、收藏、浏览热度 | 匹配 / 录书 / 触达 |
| `similar_books` | 找同类或同作者的其他书 | 匹配 / 伴读 |
| `hot_books` | 近期借阅榜，用于冷启动 | 匹配 / 触达 / 伴读 |
| `user_profile` | 当前读者的偏好聚合（分类、标签、活跃度） | 匹配 / 伴读 / 触达 |
| `user_history` | 当前读者最近借过的书 | 匹配 / 伴读 |
| `list_activities` | 已发布/进行中的活动 | 触达 / 伴读 / 匹配 |
| `activity_detail` | 单个活动详情与报名情况 | 触达 / 伴读 |
| `activity_audience` | 报名人群的学院与年级分布 | 触达 |

**为什么要场景白名单**：伴读场景不该能查「这场活动报名的人都是哪个学院的」。工具白名单是最省事也最可靠的越权防线——比在提示词里写十遍「不要查别人」管用。

每次调用都记进 `ctx.trace`，落库到 `agent_runs.tool_calls`。出问题时能回答「这次为什么推荐了这本书」。

## 五、运行时的四道闸

| 闸 | 默认值 | 超了会怎样 |
|---|---|---|
| 步数上限 | 4 步 | 最后一步不再给工具，强制模型基于已有信息作答 |
| token 预算 | 6000 | 停止继续调工具，输出已有结论并标降级 |
| 单次超时 | 45 秒 | 报 `LLMUnavailable`，重试 1 次后降级 |
| 工具结果长度 | 3500 字符 | 截断并标注，防止一次书目列表挤爆上下文 |

4 步够不够？够。本项目的场景最多是「查画像 → 找候选 → 核库存 → 出结论」，四步。真实模型下偶尔会用 3 步。

## 六、降级链

```text
真实模型可用 ──> 正常执行
     │
     ├─ 没配 key / 主动关闭 ──> 规则引擎（fallback.py）
     ├─ 余额不足 / 限流     ──> 规则引擎 + 提示管理员
     ├─ 网络超时            ──> 重试 1 次 → 规则引擎
     └─ 模型输出不合格       ──> 规则引擎（保留模型部分结果）
```

**规则引擎不是摆设**，它做的是确定性计算而不是瞎编：

- 匹配：按中图法分类占比加权 + 关键词命中 + 库存过滤
- 录书：正则抽 ISBN/书名/作者，按主题词映射分类号
- 触达：套活动字段生成三段式文案
- 伴读：书名命中 → 报馆藏；活动关键词 → 列活动；借阅规则 → 明确说不给具体数字

**降级必须被看见**：所有降级返回都带 `degraded: true` 和 `degraded_reason`，前端顶部显示黄色提示条。悄悄降级比降级本身更糟——用户会以为 AI 就这水平。

## 七、数据：先用 AI 模拟，真实数据到了再替换

学校脱敏数据要等审批，但智能体不能干等。所以做了 `scripts/simulate_data.py`。

**为什么不能随机造数据**：推荐效果取决于数据里有没有可学的模式。随机数据生成出来，推荐结果是乱的，演示时说不清「凭什么推这本」。

生成规则是刻意设计的：

```text
学院 → 主兴趣分类（计算机学院偏 TP，人文学院偏 I/K/B，经管偏 F）
借阅 → 主分类 60% / 次分类 25% / 跨类 15%
时间 → 学期内密集、寒暑假稀疏
收藏 → 从借过的书里挑，评分集中 4-5
```

跑出来的效果（实测）：

| 学院 | 借阅分布 | 推荐结果 |
|---|---|---|
| 计算机学院 | T:7 O:2 | 软件随想录、深度学习、Python数据分析 |
| 人文学院 | I:8 O:1 | 许三观卖血记、球状闪电、红楼梦 |
| 经济管理学院 | F:7 C:1 | 置身事内、贫穷的本质、高效能人士的七个习惯 |
| 理学院 | O:6 B:1 | 高等数学、从一到无穷大、数学分析 |

**来源标记**：所有模拟数据带 `data_source='simulated'`，涉及 users / books / borrow_records / book_favorites / reading_events 五张表。

```bash
# 生成（默认 200 学生 / 1600 借阅 / 105 本书）
python scripts/simulate_data.py

# 真实数据到了，精确清除模拟数据（不碰真实数据）
python scripts/simulate_data.py --purge --purge-books
```

`GET /agents/dataset` 返回当前数据构成，前端在页面顶部显示「当前包含 AI 模拟样本」。

模拟账号：`SIM20260000` 起，密码 `123456`，可以直接登录演示。

## 八、隐私边界

| 事项 | 怎么做的 |
|---|---|
| 他人借阅 | `user_profile` / `user_history` 只读当前登录用户，参数里根本没有 user_id |
| 推荐理由 | 禁止出现「和你相似的同学」「其他人也借过」这类可反推个人的说法，写进提示词也写进降级模板 |
| 访客 | 不接真实模型，直接规则推荐，理由只描述书 |
| 模拟数据 | 单独标记，可一键清除，不会混进真实统计 |
| 运行记录 | 存的是过程（调了哪些工具、几步、多少 token），不存问答正文 |

`agent_runs` 里 `input_summary` 只存前 120 字，是为了排查问题，不是为了留档。

## 九、换模型怎么换

改 `backend/.env` 三行，业务代码不动：

```bash
# DeepSeek
LLM_PROVIDER=deepseek
LLM_MODEL=deepseek-chat
LLM_API_BASE=https://api.deepseek.com/v1
LLM_API_KEY=sk-xxx

# 通义千问
LLM_PROVIDER=qwen
LLM_MODEL=qwen-plus
LLM_API_BASE=https://dashscope.aliyuncs.com/compatible-mode/v1

# 本地 Ollama（不需要 key，答辩断网也能演示）
LLM_PROVIDER=ollama
LLM_MODEL=qwen2.5:7b
LLM_API_BASE=http://127.0.0.1:11434/v1
```

三种都走 OpenAI 兼容协议，`llm_client.py` 不需要改。

**不支持 function calling 的模型也能用**：运行时会判断，模型没返回 `tool_calls` 就看文本里有没有 `{"action": "工具名", "args": {...}}`。这条兜底路径让本地小模型也能跑工具调用。

```bash
cd backend

# 1. 智能体链路（25 项，含假模型驱动的 ReAct 循环）

# 2. 前两阶段回归（7 组）
.venv/Scripts/python.exe tests/test_api_smoke.py

.venv/Scripts/python.exe -c "

"
```

页面：`/agents` 智能体工作台。左侧选场景填需求，右侧看到：

- 模型状态（可用 / 降级及原因）

轨迹那一栏是这次改动最值得看的地方——它把「模型做了什么」变成了可见的东西。

## 十一、当前限制

| 项 | 现状 |
|---|---|
| 真实模型 | key 已失效（HTTP 401），当前全部走降级。代码路径已用假模型验证过 |
| 录书 OCR | 只接收文字，没有接图片识别。前端可以先接第三方 OCR 再传文本 |

| 伴读多轮 | 有会话表，但只用最近 4 条，长对话会丢早期上下文 |

| 成本控制 | 只做了 token 预算，没有按用户配额限流 |
